# Communication Service — Integration Guide for Calling Services

**Audience:** teams integrating a service that asks the Communication Service to send a
notification — an OTP, a confirmation, an alert.

This document covers the **caller boundary only**. It is the complete surface available to a
calling service; there is nothing else you need and nothing else you can reach.

The machine-readable reference is generated from the running code and served by the service
itself:

```
GET  /openapi.json      OpenAPI 3.1, generated by reflection over the route table and DTOs
GET  /docs              Swagger UI for the same document
```

Generate your client from that. It cannot drift from the implementation — a field added to a
struct appears in the schema automatically, and a route removed disappears rather than lingering.
**This document explains what the schema cannot: the guarantees, the orderings, and the failure
modes.** Read it once before writing the client.

## 1 · The one guarantee that shapes everything

**Nothing retries. Ever.**

The service claims a notification and commits that claim *before* contacting the provider. A
crash mid-hand-off therefore leaves the notification unsent rather than sending it twice. Nothing
picks it up again.

This is the correct trade for a one-time code — a duplicate OTP is worse than a missing one — and
you must design your integration around it:

- **`failed` is final.** There is no later attempt. If your flow needs the user to receive
  something, you must decide what to do, usually by submitting again with a **new** `request_id`.
- **A missing notification is your problem to notice.** The platform surfaces stuck hand-offs to
  its operators, but nothing calls you back to say a message never left.
- **Do not build a retry loop that reuses the same `request_id`.** It will return the original
  result, not send again — see [§5](#5--request_id-is-an-idempotency-key).

The corollary is that submission is cheap and safe, and everything after it is asynchronous. A
`201` means *accepted for delivery*, nothing more.

## 2 · Reaching the service

The caller boundary is a **separate listener on its own port** from the platform's management and
provider-callback surfaces. That separation is the access control: management routes are not
merely forbidden on this port, **they do not exist on it**. A request for one returns `404`
because there is no such route here, not because a check rejected you.

| | |
|---|---|
| Port | `8085` |
| Bind | **loopback in production** |

Because it binds loopback, the service is not reachable across the network by design. Reach it
the way your estate already reaches internal services — the mesh, an SSH tunnel, or whatever
terminates and verifies service identity in your environment. **Nothing on the host verifies the
identity header itself** (see [§3](#3--headers--complete)), so the bind address is the entire
access control and the port must never be exposed directly.

Get the actual host from whoever runs the deployment; it is not part of this contract.

## 3 · Headers — complete

This is every header that matters on this boundary. There are no others: no rate-limit headers,
no correlation-id echo, no versioning header, no authentication scheme beyond the one below.

### Request headers

| Header | Required | Value |
|---|---|---|
| `X-Service-Principal` | **Always** | Your service's verified identity, e.g. `svc-auth` |
| `Content-Type` | On `POST` | `application/json` |

**`X-Service-Principal` is a header and never a body field, and that is deliberate.** Your
service does not get to *state* who it is. Something upstream — a mesh sidecar, a gateway, an
mTLS terminator — verifies the caller and *writes* this header; this service only reads it. A
body field would let any service put another's principal in its JSON and send on that caller's
permissions.

In most deployments **your infrastructure sets this header and your application code does not**.
Confirm which is true for you before hard-coding it.

Absent or empty, the answer is `401 no_caller_identity`. There is no anonymous principal, no
default, and no shared fallback to fall back to.

```http
POST /v1/notifications HTTP/1.1
Host: comms:8085
Content-Type: application/json
X-Service-Principal: svc-auth
```

### Response headers

| Header | Value |
|---|---|
| `Content-Type` | `application/json` |

That is the complete list. Every response body — success and error alike — is JSON.

### Registration is separate from identity

Presenting a valid principal is not the same as being allowed to send. Your principal must also
be **registered as a caller** in the platform, with an explicit list of permitted channels. Both
are configured by the platform's operators before you can send anything:

| Situation | Answer |
|---|---|
| No principal header | `401 no_caller_identity` |
| Principal not registered | `403 caller_not_registered` |
| Registered but deactivated | `403 caller_inactive` |
| Channel not in your permitted list | `403 channel_not_permitted` |

Ask the platform team to register your principal and grant the channels you need. A caller
granted `{sms}` submitting on `email` is refused even though the template and the address are
both perfectly valid.

## 4 · `POST /v1/notifications` — submit

Submits **one** notification. Returns once it is durably accepted; delivery happens afterwards.

> **Today this route sends on exactly one channel per call.** `template_keys` and `channels`
> are arrays because the wire contract is already the multi-channel shape, but a validation
> gate restricts each to **exactly one element**. More than one in either is
> `400 multi_template_not_supported`.
>
> To reach a person on both SMS and email, make **two calls** with **two different
> `request_id` values**. Send them as arrays of one — that way nothing on your side changes
> when the restriction is lifted.

### Request

```http
POST /v1/notifications HTTP/1.1
Content-Type: application/json
X-Service-Principal: svc-auth

{
  "template_keys":   ["otp_email"],
  "channels":        ["email"],
  "contact_details": { "email": "user@example.com" },
  "request_id":      "login-otp-2026-08-20-8f3a1c",
  "parameters":      { "company_name": "Thinq", "otp": "724386" }
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `template_keys` | `string[]` | **yes** | Which message to send, **by key** — never by version id. Exactly one element today |
| `channels` | `string[]` | **yes** | Exactly one element today, **paired by position** with `template_keys` |
| `contact_details` | `object` | **yes** | Where to send, **keyed by channel**. See [§6](#6--contact_details--where-to-send) |
| `request_id` | `string` | **yes** | Your idempotency key. See [§5](#5--request_id-is-an-idempotency-key) |
| `parameters` | `object` | usually | Template variables. Must match the template's declared set **exactly** |

The same OTP on SMS — **note that almost nothing carries over**:

```json
{
  "template_keys":   ["otp"],
  "channels":        ["sms"],
  "contact_details": { "sms": "+919451740121" },
  "request_id":      "login-otp-2026-08-20-8f3a1c-sms",
  "parameters":      { "code": "724386" }
}
```

**A template is authored per channel**, so the SMS wording and the email wording are different
keys — not one key on two channels. And because they are different templates, **they declare
different variables**:

| Channel | `template_key` | `parameters` |
|---|---|---|
| Email | `otp_email` | `company_name`, `otp` |
| SMS | `otp` | `code` |

The same one-time code is `otp` on one channel and `code` on the other. There is no convention
here and no mapping the platform applies for you — **each template's variable names are whatever
its author declared**, and sending the wrong set is `422 parameter_contract`.

The values above are this deployment's current templates, shown to make the point concrete. **Ask
the platform team for the exact `template_key` and variable list for every message you intend to
send**, and treat that list as part of your integration rather than something to infer.

**`template_keys` and `channels` are paired by position**, not crossed. Index 0 of one goes with
index 0 of the other. Unequal lengths are refused with `template_channel_length_mismatch` rather
than being silently zipped — and that check runs **before** the one-element gate, so a caller
sending two keys and one channel is told about the disagreement, which is the problem it can act
on.

#### `template_keys` names a key, not a version

You name `otp_email`; the platform resolves it to whichever version is currently active. This
means **the wording can change under you without a deploy on your side** — a typo fix, a
re-registered DLT pattern, a new sender header.

What must *not* change under you is the **variable set**. The platform's authoring rule is: same
variables → a new version under the same key; different variables → a **new key**. If your
`parameters` stop matching, you will see `422 parameter_contract`. If that ever happens without
you having changed anything, the rule was broken on the platform side — report it rather than
working around it.

You never send a version id, and there is no way to pin one. The version actually used is
returned to you as `template_id` in the response and recorded permanently, so the audit trail
still says exactly which wording was sent.

#### `contact_details` is required for every channel you request

There is no central user directory behind this service, so **you supply the address**. Every
channel in `channels` must have a matching entry in `contact_details`.

Miss one and the answer is `400 recipient_required`, refused before anything is recorded — a
message with no recipient cannot be delivered whatever its wording, and refusing it while you
still hold the request is better than accepting one that dies later in another process.

See [§6](#6--contact_details--where-to-send) for the rules on the values themselves. They are
strict, and the strictness is a personal-data rule rather than a tidiness one.

#### `parameters` must match exactly

Not a superset, not a subset. A template declaring `{company_name, otp}` requires exactly those
two keys. A missing key and an extra key are both `422 parameter_contract`.

This strictness is load-bearing rather than fussy: at least one provider accepts unknown variable
names silently, sends the message with an **empty placeholder**, and reports success. The exact
match is the only thing standing between a typo in your key name and a customer receiving an OTP
email with a blank space where the code should be.

### Response — `201 Created`

```json
{
  "submission_id": "b4e96ba5-8650-576f-aef4-0ac0a955aebc",
  "replayed": false,
  "notifications": [
    {
      "id": "d2c76940-f797-49b9-9e7f-60dec8593776",
      "template_id": "91dec3c1-c0b1-41b8-8a1b-71633d632139",
      "channel": "email",
      "status": "accepted"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `submission_id` | Identifies the whole submission. Derived from your `request_id` |
| `replayed` | `false` on first acceptance, `true` when this was a repeat — see [§5](#5--request_id-is-an-idempotency-key) |
| `notifications[].id` | **Store this.** It is what you use to read status later |
| `notifications[].template_id` | The exact version resolved. For your audit trail |
| `notifications[].channel` | Echoed back |
| `notifications[].status` | Always `accepted` at this point |

The array holds **one** entry today, for the single `(template_key, channel)` pair you sent. It
is an array because it will hold one per pair when multi-channel submission ships.

**Persist `notifications[].id` before you return to your own caller.** It is the only handle on
the notification, and there is no way to look one up by `request_id`.

### Submission is all-or-nothing

Any failure returns before a single row is written. This is trivially true while one pair is the
maximum, and it is the guarantee that keeps holding when multi-channel submission ships: you will
never get a partial submission where two channels went and one did not.

## 5 · `request_id` is an idempotency key

Not a log tag. It is what makes a retried HTTP call safe.

**Same `request_id` from the same caller → the same notifications, and nothing sent a second
time.** The response repeats the original `notifications` array with `replayed: true` and a
`200` rather than `201`.

| Call | Status | `replayed` |
|---|---|---|
| First | `201 Created` | `false` |
| Repeat, same `request_id` | `200 OK` | `true` |

The identity is scoped to **you**: your `request_id` cannot collide with another caller's.

### How to choose one

**One `request_id` per intent, not per attempt.**

- Your HTTP call times out and you do not know whether it arrived → **reuse** the same
  `request_id`. That is exactly what it is for, and it is what makes the retry safe.
- The user presses "resend code" and genuinely needs a second message → use a **new**
  `request_id`. Reusing it returns the first result and sends nothing.

Derive it from something already unique in your domain — a session id, an attempt counter, a
UUID you generate once and store alongside the operation. Do not derive it from a timestamp
alone: two rapid calls can produce the same one, and two intents can produce different ones when
you wanted a replay.

Absent or empty is `400 request_id_required`.

## 6 · `contact_details` — where to send

A map **keyed by channel**. One entry today, matching the single channel you requested:

```json
"contact_details": { "sms": "+919451740121" }
```

```json
"contact_details": { "email": "user@example.com" }
```

Two calls, one each, to reach the same person on both.

A map rather than a third positional array beside `template_keys` and `channels`, because one
mis-ordered element sends an OTP to the wrong person and nothing about the request looks wrong.
That reasoning is about the shape it will take when several channels are allowed in one call; the
shape is already correct, so nothing changes on your side when that happens.

### Address format, per channel

| Channel | Key | Format |
|---|---|---|
| SMS | `sms` | E.164 — `+919451740121`. 8–15 digits after the country code |
| Email | `email` | `user@example.com` |

**Punctuation inside a phone number is stripped for you** — spaces, hyphens and parentheses.
`+91 94517-40121` and `+919451740121` are the same address.

> **The `+` survives only as the first character.** It is kept at position 0 and dropped
> everywhere else, so `(+91) 9451 740121` normalises to `919451740121` — a number that passes
> every check and reaches the provider **without its plus**. Do not wrap the country code in
> parentheses. Send plain E.164 and this cannot happen.

**Send the country code.** The platform does not add one and does not own a numbering plan to
guess from. A bare national number is **accepted** — ten digits is inside the 8–15 bound — so
there is no error to catch this. It is simply the wrong number, and it will be sent and billed.

> **Do not lower-case an email address before sending it.** The platform folds the **domain**
> only. The local part is case-sensitive per RFC 5321, and lower-casing it can change **who
> receives the message** — this is the most commonly shipped normalisation bug, and it
> misdelivers rather than merely mis-sorting. Send the address exactly as the user gave it.

Validation here is deliberately shallow: one `@` with something either side and a dot in the
domain. It catches a value that was never an address at all. **The provider is the authority on
whether an address is real**, and it will accept — and bill for — a well-formed address that
does not exist.

| Situation | Answer |
|---|---|
| Value invalid for its channel | `400 contact_detail_invalid` |
| Key present, value blank | `400 contact_detail_invalid` |
| Key for a channel not in `channels` | `400 contact_detail_for_unrequested_channel` |
| A requested channel has no entry | `400 recipient_required` |

### The third rule is a PII rule, and it is why the field is strict

An address the platform accepts is one it **writes** — onto the queue row, and onto the attempt
record as a mask beside AES-256-GCM ciphertext. Permanent, and in every backup.

Sending an address for a channel you did not request would persist personal data for a message
that was never sent on that channel. It is **refused rather than ignored**, because silently
dropping it means you keep sending it and neither side ever finds out.

Send exactly the addresses for exactly the channels you are asking for. Nothing more.

### The address you supply is where it goes

There is no directory to fall back on and no second opinion. What you put here is what receives
the message.

> **This matters for testing.** A plausible-looking address in `contact_details` will be
> delivered and billed. Both live providers accept anything shaped like an address and answer
> success — a number one digit off a test line, a domain that does not exist. There is **no safe
> placeholder value**. Test against requests that get **rejected**, never against requests that
> get accepted with a fake address.

## 7 · `GET /v1/notifications/{id}` — read one

Takes the `id` from the submit response.

```http
GET /v1/notifications/d2c76940-f797-49b9-9e7f-60dec8593776 HTTP/1.1
X-Service-Principal: svc-auth
```

```json
{
  "id": "d2c76940-f797-49b9-9e7f-60dec8593776",
  "channel": "email",
  "status": "delivered",
  "recipient_mask": "p**************@thinq.co",
  "address_known": true,
  "stuck": false,
  "history": [
    {
      "source": "platform",
      "kind": "handoff",
      "provider": "msg91-email",
      "provider_message_id": "a28bff65-6142-4dbd-a1ac-b4f498385fa9",
      "outcome": "dispatched",
      "occurred_at": "2026-08-20T15:58:10.062611+05:30",
      "recorded_at": "2026-08-20T15:58:10.062702+05:30"
    },
    {
      "source": "provider",
      "kind": "delivered",
      "provider": "msg91-email",
      "provider_message_id": "a28bff65-6142-4dbd-a1ac-b4f498385fa9",
      "outcome": "delivered",
      "reason": "Delivered",
      "occurred_at": "2026-08-20T15:58:18+05:30",
      "recorded_at": "2026-08-20T15:59:16.314116+05:30"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `status` | The current status. See [§8](#8--status-vocabulary) |
| `recipient_mask` | A **mask**, never the address. `null` when none was recorded |
| `address_known` | Whether an address was ever recorded — see below |
| `stuck` | The hand-off started and never finished. A human needs to look |
| `history[]` | Every lifecycle event, from both sources |

The response also carries a `user_id` field. **Ignore it** — it is a remnant of an earlier
contract, it is always empty, and there is nothing you can put in the request to populate it. It
appears in the generated OpenAPI schema for the same reason; your client will have the field and
should never read it.

### `address_known: false` is a positive statement

It means **no address was ever recorded**, so the provider was never contacted and nothing was
sent. That is a stronger and more useful answer than a `null` mask, which could mean either "not
sent" or "sent, mask not recorded". Together with `recipient_mask: null`, it is proof of a
non-send.

### `history[]` — two sources, and the ordering is ours

| `source` | Meaning |
|---|---|
| `platform` | What **we** did — the hand-off, an operator triage |
| `provider` | What **they** reported — accepted, delivered, bounced, opened |

The two are kept distinguishable deliberately. Merging them is how an `opened` report — which is
later than the delivery it follows — ends up sorting above the hand-off that caused it.

> **The array is ordered by `recorded_at`, our clock — when we learned it — not by
> `occurred_at`, the provider's clock — when it happened.**
>
> These differ, and not only by milliseconds. A provider can deliver two webhooks out of order,
> or retry an older one hours later. In the example above, `delivered` appears **before** `sent`
> in the array because the delivered webhook was ingested first.
>
> **If you want provider chronology, sort by `occurred_at` yourself.** Do not assume array order
> is event order. `occurred_at` on a `provider` entry is the provider's own timestamp, and it is
> the field to use for "when did this actually happen".

### Not-found and not-yours are indistinguishable

A notification belonging to another caller returns `404 not_found` — byte-identical to one that
does not exist. This is deliberate: a different answer would let you discover which ids exist by
probing.

## 8 · Status vocabulary

Ten values. The first four are the platform's own record of what it did; the rest come from the
provider.

| Status | Meaning |
|---|---|
| `accepted` | Durably queued. Nothing has been sent |
| `claimed` | A worker has taken it and is handing it off |
| `dispatched` | Handed to the provider, which accepted it. No delivery report yet |
| `failed` | Terminal. Never sent, and **nothing will retry** |
| `sent` | The provider reports it left their system |
| `delivered` | The provider reports it reached the recipient — **read the warning below** |
| `bounced` | Rejected by the receiving system. Terminal |
| `rejected` | The provider refused it. Terminal |
| `dropped` | The provider discarded it, e.g. a suppression list. Terminal |
| `expired` | Never confirmed within the window |

`accepted` → `claimed` → `dispatched` is the normal path, and a notification can sit at
`dispatched` indefinitely on a channel with no delivery reporting.

### `delivered` means different things on different channels

> **On email**, it is a genuine delivery report from the provider.
>
> **On SMS, it means the vendor accepted the message — not that a handset received it.** The SMS
> aggregator publishes no delivery-report mechanism at all, so acceptance is the strongest signal
> that exists, and it is recorded as `delivered` on the derived status. Every notification
> affected carries a `SYNTHETIC_ACCEPT_NO_DLR` marker in its provider event record.

**Do not build a flow that treats SMS `delivered` as proof a customer saw the message.** It is
proof the vendor took it. If a decision depends on genuine delivery, it cannot be made on SMS
today.

## 9 · Error reference

Every error response has the same shape and no free text:

```json
{ "error": "Bad Request", "reason": "contact_detail_invalid" }
```

**`reason` is the entire message.** Branch on it; never parse `error`, which is only the HTTP
status text. There are many distinct reasons rather than one code with a detail string,
precisely so that this is possible.

### `401` — identity

| Reason | Cause |
|---|---|
| `no_caller_identity` | `X-Service-Principal` absent or empty |

### `403` — permission

| Reason | Cause |
|---|---|
| `caller_not_registered` | Your principal is not a registered caller |
| `caller_inactive` | Registered but deactivated |
| `channel_not_permitted` | That channel is not in your granted list |

None of these is fixable from your side. Talk to the platform team.

### `400` — your payload, and you can fix it

| Reason | Cause |
|---|---|
| `malformed_body` | Not valid JSON, or an unrecognised field. **A caller still sending `template_ids` or `contact_no` lands here** |
| `request_id_required` | Absent or blank |
| `channels_required` | Absent or empty |
| `channel_unsupported` | Not one of `sms`, `email`, `whatsapp` |
| `channel_repeated` | The same channel twice |
| `template_key_repeated` | The same key twice |
| `template_channel_length_mismatch` | `template_keys` and `channels` have different lengths |
| `multi_template_not_supported` | More than one element in `template_keys` or `channels`. One per call today — send two calls with two `request_id` values |
| `recipient_required` | A requested channel has no `contact_details` entry |
| `recipient_address_invalid` | A resolved address is not valid for its channel |
| `contact_detail_invalid` | The value is malformed for its channel, or blank |
| `contact_detail_for_unrequested_channel` | An address for a channel not in `channels`. See [§6](#6--contact_details--where-to-send) |

### `422` — well-formed, but the platform refuses it

The request parsed and every field is valid. **You usually cannot fix these by editing the
payload.**

| Reason | Cause |
|---|---|
| `template_not_found` | No template with that key |
| `template_not_live_on_channel` | The key exists but has no active version for that channel |
| `parameter_contract` | `parameters` does not match the template's declared variables exactly |

`template_not_live_on_channel` most often means the version was deactivated, or was authored in a
locale that cannot be reached. Either way it is a platform-side fix.

### `404` — not found

| Reason | Cause |
|---|---|
| `not_found` | No such notification, **or** it belongs to another caller |

### `500` — ours

| Reason | Cause |
|---|---|
| `internal_error` | A failure on our side. Nothing was sent unless a later read says otherwise |

**A `500` on submit is genuinely ambiguous** — the notification may or may not have been
accepted. Retry with the **same `request_id`**; if it was accepted, you get the original result
back with `replayed: true` and nothing is sent twice. This is the case idempotency exists for.

## 10 · Things that will bite you

Collected here because each one has already caused a real problem.

**1 · One channel per call.** `template_keys` and `channels` are arrays but each takes exactly
one element today. Two channels means two calls with two `request_id` values, not one call with
two array entries. Build it as arrays of one and nothing changes when the restriction lifts.

**2 · `template_ids` and `contact_no` no longer exist.** If you are integrating against an older
version of this contract, both now return `400 malformed_body`. They became `template_keys`
(string keys, not UUIDs) and `contact_details` (a map keyed by channel).

**3 · `locale` is not on the wire and cannot be sent.** A locale belongs to the recipient, so a
caller supplying one is a caller guessing. It is fixed at `en` today.

**4 · A `201` is not a delivery.** It means durably queued. Everything after it is asynchronous,
and on SMS you may never learn more than "the vendor took it".

**5 · SMS `delivered` is vendor acceptance.** See [§8](#8--status-vocabulary). This is the single
most common misreading of this API.

**6 · `history[]` is in ingest order, not event order.** Sort by `occurred_at` if you need
provider chronology.

**7 · Nothing retries.** `failed` is final. If your flow needs the message to arrive, you must
submit again with a **new** `request_id`.

**8 · There is no safe test address.** Both providers accept and bill anything address-shaped,
and `contact_details` bypasses address resolution. Exercise the path with requests that get
**rejected**.

**9 · Polling for status has no rate limit and no push.** There are no webhooks to you and no
callback registration. If you poll, poll on a backoff — status changes are seconds apart at best,
and on SMS the terminal state arrives at hand-off and never changes again.

## Getting set up

Before your first successful call, the platform team must:

1. **Register your `X-Service-Principal`** as a caller, with the channels you need granted.
2. **Author the templates** you intend to name, active on those channels, and tell you the
   `template_key` and the exact `parameters` each one declares.

Confirm both before you start, and confirm with your own infrastructure team **who sets
`X-Service-Principal`** — in most deployments it is written by the mesh or gateway rather than by
